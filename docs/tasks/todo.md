# Текущие задачи PharmNode

## Инструкции для AI-агента:
> **Контекст**: Проект использует Paddle Billing v2 в качестве платежной системы на стеке Next.js (App Router) + TypeScript + Prisma/PostgreSQL.
> **Архитектура**:
> Frontend — интеграция Paddle SDK через `@paddle/paddle-js`. Инициализация в `src/components/PaddleInit.tsx`.
> Backend — Route Handlers для приема вебхуков от Paddle (`/api/webhooks/paddle`) и валидации подписи с помощью `@paddle/paddle-node-sdk`.
> **Критические правила**:
> 1. Писать только чистый, production-ready TypeScript со строгой типизацией.
> 2. Мы используем **Paddle Billing v2**, а не Stripe, Lemon Squeezy или PayPro Global.
> 3. В обработчиках вебхуков **обязательно** применять валидацию подписей с использованием `PADDLE_WEBHOOK_SECRET`.
> 4. Не делать внутренний UI для управления картами/подписками. Использовать внешний Customer Portal.
> 5. Фокусироваться на безопасной обработке краевых случаев (проверка подписей, отсутствие `userId`, неверные статусы и т.д.).
> 6. **Покрытие тестами**: Все новые фичи должны быть покрыты автоматическими тестами, особенно это касается логина (авторизации) и оплаты (подписок/вебхуков).
> 7. **Запрет на мануальное тестирование AI**: AI не проводит мануальное тестирование. Вместо этого AI должен расписывать задачи по мануальному тестированию и передавать их пользователю для самостоятельной проверки.

---

## ⚠️ Архитектурный контекст (Schema v2.0)

> **Философия**: Детерминированная экспертная система (DSS), все расчёты выполняются **на клиенте** (Front-end First).
> Back-end = Source of Truth (хранение, авторизация, защита API).
> Фронтенд загружает JSON-справочники и использует `src/lib/calculator.ts` для вычислений в реальном времени.

## 🐛 Бэклог багов и улучшений: Система авторизации (Infinite Loop Fix)

### 1. [x] Исправление бесконечного цикла редиректов (Infinite Loop)
- **Проблема:** При попытке входа (особенно для mock-пользователей) `middleware.ts` пропускает запрос по куке `pharmnode_mock_user`, но `src/app/(protected)/layout.tsx` ожидает строгой NextAuth сессии (`getServerSession`). Из-за отсутствия NextAuth сессии `layout.tsx` редиректит на `/login`. На странице логина клиентский стейт видит mock-юзера и редиректит обратно на `/projects`. То же самое происходит при рассинхронизации клиентской и серверной NextAuth сессии.
- **Задача:** Добавить обработку `pharmnode_mock_user` в `src/app/(protected)/layout.tsx` (только для не-production среды), чтобы он пропускал mock-сессии так же, как это делает `middleware.ts`.

### 2. [x] Обработка протухших сессий на клиенте (SessionExpired)
- **Проблема:** Если сессия удалена из БД (`UserSession`), NextAuth токен (в `src/lib/auth.ts`) получает флаг `error: "SessionExpired"`. Сервер (в `layout.tsx`) отклоняет такие сессии, но клиентский стейт `useSession` может всё ещё считать `status === "authenticated"`, что приводит к бесконечному циклу для реальных пользователей.
- **Задача:** В `src/context/AuthContext.tsx` отслеживать состояние `session.error === "SessionExpired"`. Если ошибка присутствует, принудительно вызывать очистку стейта на клиенте (и `signOut()`).

### 3. [x] Унификация проверок авторизации
- **Проблема:** Логика проверки авторизации размазана между `middleware.ts` (проверяет куки и токены), `layout.tsx` (проверяет БД и NextAuth) и `AuthContext.tsx`.
- **Задача:** Упростить и стабилизировать систему логирования, вынеся общие проверки (isMockAuthenticated, isAuthenticated) в единый узел, чтобы защитный механизм работал синхронно везде. (Защиту оставить на текущем уровне, если потребуется изменить принципы — запросить согласование).

### 4. [x] Покрытие тестами (Авторизация)
- **Задача:** Написать автоматические тесты для флоу авторизации:
  - Обработка невалидной/протухшей сессии (проверка отсутствия infinite loop).
  - Вход под mock-пользователем (в dev/sandbox).

### 5. [x] Мануальное тестирование (Для пользователя)
- **Задача:** После реализации кода, подготовить шаги тестирования для пользователя (чистка кук, попытка входа под mock и credentials).
